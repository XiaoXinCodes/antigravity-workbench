# 跨窗口暂停：协议设计与合约阻断

2026-10-22。**以下原始设计及反例保留为历史调查，不是当前版本支持声明。** 最新授权接受有限、可验证的官方 1.8.0 ready 适配，操作期间用户不得新开、重连或更改官方启动配置；不再要求技术上禁止所有未来进程。源码指纹、当前进程出生身份、逐次写入 guard 和未知凭据保护仍不可放宽。

## 当前实施状态

有限官方 1.8.0 ready 适配已接入默认 WSL 切号、跨宿主协调和恢复按钮；最终范围、回归证据及未验收项见 [组件切号候选验证](VALIDATION_COMPONENT_SWITCH_CANDIDATE.md)。下文保留旧的绝对暂停设计与反例，不作为本候选承诺。

## 最小协议

1. 注册不能代替发现。可信宿主清单必须覆盖同凭据范围内所有活扩展宿主，包括无 Hub、Workbench 未激活、旧版或未安装 Workbench 的宿主。身份包含平台/用户、凭据范围的实际文件身份、boot/session、PID 与启动身份；不能仅信任注册文件中的自报 PID、工程名或端口。未知范围阻断。
2. 用户确认受影响窗口和任务后，协调者持有现有跨窗口事务互斥，持久化随机事务 ID、参与者启动身份和准备状态。每个参与者验证请求来源及凭据范围，取得本实例的持续暂停句柄。ACK 必须绑定事务、宿主启动身份、官方实例代际和暂停句柄，不能接受旧 ACK。
3. 所有参与者暂停完成且新实例启动准入已关闭后，才能开始写入。写入和存储读回完成后持久化 installed 状态；这不等于线上身份验收。在保留全局事务及其他参与者暂停的条件下，仅授权指定验证 Hub 启动并执行 fresh RPC。若需回滚，先重新取得该验证 Hub 的暂停确认，再写入旧凭据。写入、回滚及恢复备份适用同一保护，不能只保护第一次写入。
4. 线上验收或回滚收尾完成、持久化终态后，才释放全体暂停并逐个恢复。恢复失败保留准确结果和单窗口重试入口，不撤销已成功的凭据事务，也不自动再次切号。
5. 超时/取消在写入前撤销准备；进入写入后由事务执行者完成提交或回滚，再释放。协调者失联时，参与者保持暂停，独立恢复者必须证明旧执行者退出、接管互斥并恢复 journal 后才可恢复。单纯租约到期不能证明旧写入已结束。

## 故障矩阵

| 条件 | 必须采取的动作 |
| --- | --- |
| 无 Hub 的活宿主 | 必须纳入发现及暂停；不能按没有 agy 忽略 |
| 旧版、未参与、来源无法验证 | 准备失败，说明具体窗口需升级/关闭，不结束未知进程 |
| PID 复用、旧 ACK、参与者重启 | 原凭证失效，禁止写入；新实例受启动准入约束 |
| 暂停中仍有 startingPromise/restart | 不发 ACK；等待真实 fence 完成或失败 |
| 用户 retry、配置变化、新窗口 | 官方启动必须被 fence 阻止，不能靠 UI 提示替代 |
| 准备取消或超时 | 未写入时安全撤销；已写入时交由 journal 收尾 |
| 协调者暂停、退出、网络失联 | 不按租约期限自动启动；确认旧执行者不再写入后恢复 |
| 写入或回滚失败 | 保留 journal 与暂停；明确需要恢复，不静默恢复全部后台 |
| 恢复部分失败 | 展示哪些窗口恢复成功，允许单实例重试，不重复切号 |

## 已证明的合约缺口

依据 Library 中两版完整 start/stop、renderer/provider、exports 与 1.9 自动恢复源码（详见候选验证记录）：

- 已有 stop/deactivate 只停止当前引用，不返回持久暂停句柄。start 不读取 Workbench 的注册表、租约或事务锁。停止后 renderer setup/retry 可以再次启动。该反例明确涉及真实启动入口，不假设任意恶意外部代码。
- 1.9 已开始的 restart 在 await stop 后继续 start；另一次 stop 的返回不取消前一条链。此前同宿主 ready 条件证明只能排空特定已有链，不能获得持续禁止启动的能力。
- Workbench 尚未激活的新宿主不能先注册后被阻止。后台扫描只见 agy，也不能发现此时无 Hub 的活宿主。重复扫描仍不能关闭“最后扫描后新宿主启动”的空隙。
- 合作租约到期不证明协调者死亡或 OS 写入结束。用超时自动恢复后台会与尚在完成的写入/回滚冲突。

`test/cooperative-pause-contract.test.cjs` 用纯合成模型重现以上缺口；它是反例证据，不是修复已通过的回归。没有运行官方包或真实进程。

## 能兑现协议所需的最小能力

首选由官方实现共享凭据范围的可等待 pause/resume：同步关闭所有启动入口，排空在途启动/恢复，返回持有期间不可启动的句柄，并支持在全局暂停期间仅授权指定实例进行线上验证；新实例首次启动前也检查该范围的 fence。Workbench 才能安全实现上述协调与恢复。这不是通过调用现有 reconnect/stop 能获得的接口。

另一方向是独立平台执行器控制所有相关扩展宿主及新宿主启动，保留编辑器窗口但暂停宿主内全部扩展。仅向已知 PID 发暂停信号仍不满足新宿主准入；Windows/WSL 两侧控制、执行器崩溃恢复和文件写入收尾均需单独设计及验证。当前授权不包含实际操作用户宿主，且此路线影响范围大于暂停官方后台，不能偷偷替换。

在获得上述能力前，不实现会错误 ACK 的合作暂停，也不构建声称支持多窗口切号的新候选。旧 v2 全禁用候选仍不可交付。现有组件重启修复与这些跨宿主凭据事务限制分开。
